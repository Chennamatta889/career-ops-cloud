Kubernetes

Diagnose Kubernetes Pods that will not start

A structured approach to Pending, ImagePullBackOff, CrashLoopBackOff, and readiness failures.

By Career-Ops · Published 21 November 2026 · Practical guide

Get the actual state

Begin with the namespace, Deployment, ReplicaSet, and Pod status. Check events and container state before changing anything. Useful commands include 'kubectl get pods -n NAMESPACE', 'kubectl describe pod POD -n NAMESPACE', and 'kubectl logs POD -n NAMESPACE --previous' for recently restarted containers.

Do not assume every failing Pod is an application bug. Scheduling, image pull, configuration, security context, and runtime health are separate failure classes.

Pending and image pull problems

A Pending Pod may have insufficient requested CPU or memory, an unsatisfied node selector, missing tolerations, or a storage binding issue. Read scheduler events and inspect node capacity. Changing requests blindly can move the failure into production load.

ImagePullBackOff commonly points to an incorrect image name or tag, registry connectivity, or image-pull authentication. Verify that the exact immutable artifact exists and that the workload's service account has the needed pull permissions.

Crash loops and probe failures

CrashLoopBackOff indicates repeated container exits; inspect both current and previous logs and the termination reason. Common causes include configuration errors, unavailable dependencies, permission problems, and out-of-memory kills. A failed readiness probe may keep traffic away even while the container is running.

  • Use logs and exit codes to locate an application startup error.
  • Inspect environment variables and mounted configuration without exposing secret values.
  • Check whether probe path, port, delay, and thresholds match the real application.
  • Verify downstream dependencies such as DNS, databases, and service endpoints.

Make a reversible fix

Choose the smallest defensible change, apply it through the normal deployment process, and observe the rollout. Confirm both Kubernetes readiness and real user-facing health. If the release degraded service, follow the team's rollback procedure. Avoid deleting arbitrary production Pods as a substitute for diagnosis.

Document the incident sequence: symptom, event, root cause, mitigation, verification, and prevention. The best troubleshooting habit is preserving evidence before it disappears.
